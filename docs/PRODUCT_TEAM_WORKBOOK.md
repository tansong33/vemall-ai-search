# AI 商城智能搜索：产品团队工作手册

> 版本：V1.0<br>
> 基线日期：2026-07-22<br>
> 适用对象：搜索意图与标注、业务规则与相关性、体验数据与验收 3 名产品负责人<br>
> 使用方式：会前阅读、会上认领、会后按模板直接填写；无需查看 GitHub 或理解代码

## 1. 先用一句话理解项目

这个项目要把用户的自然语言需求，快速转换成商城可以执行的搜索条件，然后从真实商品库返回合适商品。

例如用户搜索：

> 给员工买 50 元以内的膳魔师保温杯，要现货，可以开专票

系统需要理解：

- **买什么**：保温杯；
- **什么品牌**：膳魔师；
- **什么场景**：员工福利；
- **价格要求**：不超过 50 元；
- **其他硬条件**：有库存、可以开专票。

随后系统从数据库或搜索引擎中找到真实商品，排除违反条件的商品，再把更相关的商品排在前面。

产品团队最重要的职责不是训练模型或写技术方案，而是给系统建立一套清晰、稳定、可重复判断的“业务真值”：什么条件必须满足、什么结果算好、什么结果算错。

## 2. 用户实际会经历什么

### 2.1 输入阶段：关键词联想

用户输入“魔师”，系统可以联想到“膳魔师”；输入品牌或类目的一部分，也可以从前缀、中间或后缀找到候选词。

产品需要决定：

- 显示品牌、类目、历史词还是热搜词；
- 每次显示多少条；
- 完全匹配、前缀匹配、别名和热度如何排序；
- 用户输入错误、无联想或接口超时时页面如何表现；
- 是否展示候选词类型，例如“品牌”“类目”。

### 2.2 提交阶段：识别需求

系统先用词典和规则识别品牌、类目、场景、价格、属性等条件。未来会增加 MiniRBT 小模型，但会先在后台比较，不会立即替换现有规则。

产品需要决定：

- 一段文字应该标成什么实体；
- 同一个词有多种含义时如何判断；
- 否定词、错别字、别名、组合词怎样处理；
- 模型不确定时，是放宽检索、使用规则还是提示用户补充条件。

### 2.3 检索阶段：找到候选商品

商品编号、SKU、条码等明确标识会直接查询；普通需求优先由 Elasticsearch 搜索，必要时由 MySQL 兜底。

产品需要决定：

- 哪些商品必须进入候选；
- 同义表达是否应该找到同类商品；
- 搜不到时是否放宽品牌、属性或价格；
- 哪些条件绝对不能放宽。

### 2.4 排序与展示阶段

系统先过滤不能售卖、无库存或违反硬条件的商品，再按照文本相关性、规则分、运营分和预算贴合度排序。

产品需要决定：

- 哪些是硬条件，违反后必须排除；
- 哪些是偏好，可以通过排序体现；
- 一个 SPU 有多个 SKU 时，页面应该展示哪个 SKU；
- 无结果、少结果、降级和超时分别如何提示。

## 3. 当前已经有什么，还缺什么

### 已经可以演示和联调

- 搜索输入框关键词联想；
- 规则和商品词典识别 Query；
- 品牌、类目、场景、价格、容量、颜色、材质等条件抽取；
- SPU、SKU、条码和供应商 SKU 精确查询；
- 公司商品表查询适配；
- MySQL 有界召回和 Elasticsearch 召回接口；
- 库存、预算等硬过滤和基础排序；
- 本地缓存和可选 Redis；
- 每个搜索阶段的耗时和实际路线记录；
- NER 标注数据的导入、校验、切分和评分工具。

### 还没有达到生产上线

- 没有基于公司真实 Query 微调完成的 MiniRBT 模型；
- 没有完成全部商品向 Elasticsearch 的全量和实时同步；
- 没有冻结的 NER 金标数据和搜索相关性金标；
- 没有用约 682 万 SKU 完成真实并发、延迟和容量验证；
- 没有生产 Dashboard、告警、灰度和回滚演练；
- 价格、库存、状态、租户和渠道的部分业务口径仍需确认。

因此，当前可表述为“可运行、可测试、可分工开发的 POC 框架”，不能表述为“生产搜索已经完成”。

## 4. 三名产品的分工总览

| 角色 | 主要问题 | 核心产出 | 最紧密配合对象 |
|---|---|---|---|
| 产品 1：搜索意图与 NER 标注 | 用户这句话到底在找什么 | 标签规范、Gold Query、词典和歧义规则 | NER 开发 |
| 产品 2：业务规则与相关性 | 哪些商品能出现，先后顺序是否合理 | 业务真值表、相关性评分、Golden Query | 规则/排序、ES 开发 |
| 产品 3：体验、数据与验收 | 用户是否觉得快、准、好用 | 交互说明、埋点、指标看板、版本验收 | 前后端、缓存性能开发 |

三人需要共同维护一份“搜索问题库”。同一个问题只能有一个主负责人，但可以同时关联 NER、召回、规则和体验标签。

## 5. 产品 1：搜索意图与 NER 标注

### 5.1 需要熟悉的业务知识

- 商城类目树、品牌、商品类型和常用属性；
- 用户常用简称、别名、错别字和口语表达；
- 员工福利、办公、差旅、劳保、节日、送礼等采购场景；
- 标签边界和一致性：相似句子必须采用相同规则；
- 隐私与脱敏要求。

不要求掌握模型训练、Python 或 ONNX；需要能够对标注结果做稳定的业务判断。

### 5.2 第一周先完成什么

1. 整理第一版实体标签和定义；
2. 从脱敏历史 Query 中选取 200 条，覆盖常见与困难表达；
3. 与 NER 开发共同完成 AI/规则预标注；
4. 人工逐条复核实体文字、起止位置和标签；
5. 对歧义样本建立统一处理规则；
6. 形成 200 条双人复核 Gold Query，作为第一版基线。

### 5.3 第一版标签如何理解

| 标签 | 产品解释 | 示例 | 暂不交给模型的内容 |
|---|---|---|---|
| BRAND | 品牌及明确别名 | 膳魔师、华为 | 条码、SKU ID |
| CATEGORY | 商城标准类目 | 口罩、办公用品 | 价格区间 |
| PRODUCT_TYPE | 用户描述的商品类型 | 保温杯、风扇 | 数量和单位 |
| SCENE | 购买或使用场景 | 员工福利、差旅、送礼 | 可直接由规则识别的固定数字条件 |
| ATTRIBUTE_VALUE | 颜色、材质、功能等属性值 | 红色、不锈钢、降噪 | 明确的“不超过 50 元” |

价格、数量、容量单位、商品编号和肯定可由规则稳定识别的条件，优先使用规则，不必强迫模型学习所有内容。

### 5.4 一条 Gold Query 的样子

Query：`给员工买50元以内的膳魔师保温杯`

应标注：

- `员工` → SCENE；
- `膳魔师` → BRAND；
- `保温杯` → PRODUCT_TYPE；
- `50元以内` → 由价格规则处理，不做模型实体。

Gold Query 不是“看起来像对”的机器输出，而是经过人工确认、能够作为评分答案的样本。

### 5.5 高质量 Query 从哪里来

优先顺序：

1. 脱敏后的真实历史搜索词；
2. 客服、销售、采购和运营提供的真实表达；
3. 产品依据关键业务场景人工设计；
4. 从商品类目、品牌和属性组合生成模板 Query；
5. 大模型离线改写或生成的候选 Query。

大模型生成的内容只能进入候选池，不能直接进入 Gold 数据。必须检查是否自然、是否符合公司商品、是否包含虚构品牌或不合理条件。

### 5.6 Query 采样不能只选简单句

第一批 Query 至少覆盖：

- 高频短词：`口罩`、`办公椅`；
- 品牌 + 类目：`膳魔师保温杯`；
- 价格 + 场景：`50元以内员工福利`；
- 多属性：`黑色降噪蓝牙耳机`；
- 自然语言长句：`适合夏天办公室降暑的员工福利，要现货`；
- 否定表达：`不要玻璃材质`；
- 歧义词：既可能是品牌也可能是普通词；
- 中英文、数字、型号和单位混写；
- 错别字、简称和别名；
- 没有实体或不是商品搜索的句子。

### 5.7 标注质量要求

- 同一标签边界必须一致，例如不能一会标“保温杯”、一会只标“杯”；
- 不根据自己猜测补原文中不存在的实体；
- 不因为商品库没有某品牌就把品牌标成普通文字；
- 否定条件必须单独记录，不能按正向需求处理；
- 困难样本由两人复核，冲突必须记录原因并更新规范；
- 训练、验证、测试不能包含同模板换词造成的数据泄漏；
- 冻结后的测试集不能拿来反复调整规则或模型。

### 5.8 产品 1 的完成标准

- 有书面的标签规范和正反例；
- 有数据来源、脱敏方式、版本和修改记录；
- 第一批 200 条完成双人复核；
- 逐步扩充到约 2,000 条 POC 数据；
- 能解释模型在品牌、类目、场景和困难 Query 上分别错在哪里；
- 新增规则或别名时，同时补充回归样本。

## 6. 产品 2：业务规则与搜索相关性

### 6.1 需要熟悉的业务知识

- 商品上下架、审核、删除和品牌/类目启用状态；
- 售价、协议价、会员价、税价等价格口径；
- 总库存、锁定库存、预警库存和最小起购量；
- 租户、渠道、供应商和用户价格体系；
- SPU、SKU、条码、供应商 SKU 的区别；
- 搜索结果“完全相关、基本相关、勉强相关、不相关”的判断。

不要求写规则代码或 Elasticsearch 查询，但需要把规则写成开发和测试都能执行的真值表。

### 6.2 会议必须确认的第一批业务口径

| 待确认口径 | 结论、负责人和日期 |
|---|---|
| 搜索结果是否采用“SPU 商品卡 + 最佳匹配 SKU” | 待填写 |
| 默认价格是否使用 `sales_price` | 待填写 |
| 会员价、协议价或租户价如何选择 | 待填写 |
| 可售库存是否等于“总库存 - 锁定库存” | 待填写 |
| 小于最小起购量的 SKU 是否可以展示 | 待填写 |
| SPU、SKU、类目、品牌分别哪些状态可被搜索 | 待填写 |
| `tn_code`、`channel_code` 是否所有请求必填 | 待填写 |
| 无库存、超预算、属性不符时哪些条件绝不放宽 | 待填写 |
| 运营主推能否突破硬规则 | 待填写 |
| 零结果时的放宽顺序和用户提示 | 待填写 |

### 6.3 硬条件和软偏好

**硬条件**：违反后商品不能出现。例如无权访问的租户商品、已删除/下架商品、明确要求现货但可售库存为零、明确上限 50 元但商品价格超过 50 元。

**软偏好**：可以通过排序体现。例如“适合员工福利”“销量较好”“运营主推”“价格更接近预算”“颜色更接近但不完全一致”。

产品 2 需要为每条规则明确：适用范围、输入字段、判断条件、是否可放宽、放宽顺序、结果原因码和反例。

### 6.4 相关性 0～3 分如何打

| 分数 | 含义 | 示例：Query 为“50 元以内员工福利保温杯” |
|---:|---|---|
| 3 | 完全满足核心意图和条件 | 45 元、有库存、可采购的保温杯 |
| 2 | 主要意图正确，少量偏好不完整 | 49 元普通保温杯，员工福利标签不明确 |
| 1 | 文本有关，但不应排在前面 | 89 元保温杯，超过明确预算 |
| 0 | 不相关 | 手机壳或与保温杯无关商品 |

如果商品违反租户、上下架或库存等硬规则，应另外标记“约束违规”。不能只打低分后仍允许它出现在结果中。

### 6.5 Golden Query 怎么建设

每条 Golden Query 至少包含：

- 原始 Query；
- Query 类型和业务场景；
- 必须满足的硬条件；
- 可以放宽的软偏好；
- 期望出现的商品/类目；
- 候选商品 0～3 分；
- 不能出现的商品及原因；
- 零结果时的处理；
- 标注人、复核人、版本和日期。

第一阶段准备 100～200 条，不追求数量大，先覆盖真实主要场景和高风险规则。固定后每次模型、搜索字段、同义词、规则或权重变化都使用同一批 Query 回归。

### 6.6 产品如何看搜索指标

| 指标 | 用通俗语言解释 | 产品应该追问 |
|---|---|---|
| Recall@50/200 | 正确商品有没有进入前 50/200 个候选 | 是完全没找到，还是找到了但没排上来 |
| MRR | 第一个正确商品出现得有多早 | 用户是否需要翻很多结果 |
| NDCG@10/20 | 前 10/20 名的整体顺序是否合理 | 高相关商品是否集中在前面 |
| Zero Result Rate | 搜索后没有商品的比例 | 是无商品、条件过严还是召回失败 |
| Constraint Violation | 违反预算、库存、状态等硬规则的比例 | 哪条业务规则没有生效 |

产品不要只凭几张截图判断“效果不错”。每次版本验收需要看固定 Query 的指标变化和失败案例。

### 6.7 产品 2 的完成标准

- 价格、库存、状态、租户和渠道口径已确认并留痕；
- 硬规则与软偏好有可执行定义；
- 至少 100 条 Golden Query 完成相关性评分和复核；
- 每次版本能说明 NDCG、零结果率和约束违规率变化；
- 对 Top 失败 Query 给出“数据、NER、召回、规则或排序”的原因分类；
- 运营规则不得绕过业务硬条件。

## 7. 产品 3：搜索体验、数据和版本验收

### 7.1 需要熟悉的业务知识

- 搜索输入、联想、结果页、筛选和空状态交互；
- 曝光、点击、加购、下单、改搜等用户行为；
- P50/P95/P99、缓存命中率和错误率的基本含义；
- A/B 实验和灰度发布的基本原则；
- 不同错误、超时和降级情况下的用户提示。

不要求搭建 Redis 或监控系统，但需要明确看什么指标、什么情况算通过、什么情况必须回退。

### 7.2 关键词联想需要确认什么

- 最少输入几个字开始联想；
- 最多展示几条；
- 品牌、类目、热词、历史词的展示样式和优先级；
- 完全、前缀、中间、后缀和别名匹配如何排序；
- 是否支持拼音、首字母、错别字纠正；
- 上下键、回车、鼠标和移动端点击行为；
- 用户继续输入时是否取消旧请求；
- 无联想、慢请求和接口失败是否保持正常输入。

当前 Demo 已有 160 ms 防抖、旧请求取消和键盘选择。拼音、纠错、热词和 ES 联想仍需后续评测。

### 7.3 搜索页面状态清单

- 正常有结果；
- 结果较少；
- 没有结果；
- 条件过严，建议放宽；
- 搜索服务降级但仍有结果；
- 网络或服务异常；
- 输入为空或超长；
- 精确商品编号不存在；
- 商品已下架或无访问权限；
- 顶部未来出现异步 AI 导购文案时，文案失败不影响商品列表。

每种状态都要给出页面文案、可执行下一步和是否记录埋点。

### 7.4 第一版埋点事件

| 事件 | 最少记录 | 用途 |
|---|---|---|
| suggestion_exposure | Query 前缀、候选词、位置、类型、版本 | 联想是否有效 |
| suggestion_click | 选择词、位置、输入方式 | 哪类联想被采用 |
| search_submit | 脱敏/规范化 Query、租户渠道、版本 | 搜索量和 Query 分布 |
| result_exposure | 商品、位置、召回来源、规则/索引版本 | 结果实际被看到 |
| result_click | 商品、位置、Query | 点击相关性 |
| add_to_cart/order | 商品、Query、位置 | 搜索业务价值 |
| query_reformulation | 前后 Query、间隔、是否零结果 | 用户是否因结果不好改搜 |
| search_degrade/error | 阶段、原因、回退路线、耗时 | 体验和稳定性问题 |

所有 Query 和用户信息必须遵守公司脱敏、权限和留存要求。

### 7.5 性能指标怎么理解

- **P50**：一半请求比这个值快；
- **P95**：95% 请求在这个时间内完成，代表大部分用户体验；
- **P99**：最慢的一小部分请求，能暴露长尾卡顿；
- **缓存命中率**：多少热门请求无需重复计算；
- **降级率**：多少请求因模型、ES、Redis 等异常走了备用路线；
- **错误率**：最终没有按协议返回结果的请求比例。

最终 SLA 需要结合公司实际峰值 QPS 和环境确认。没有真实压测前，不把 Demo 耗时当作生产承诺。

### 7.6 产品验收不能只看“接口成功”

一次版本验收至少包含：

1. 高频、长尾、精确编号、多条件长句、错别字和零结果 Query；
2. 正常、冷缓存、热缓存和依赖故障场景；
3. NER、召回、排序和业务约束指标；
4. 联想、搜索、空态和错误态交互；
5. 埋点是否齐全且没有泄露敏感信息；
6. P95/P99、错误率和降级率；
7. 已知问题、影响范围、回退方案和是否允许发布。

### 7.7 产品 3 的完成标准

- 联想和结果页各状态有明确交互说明；
- 埋点协议能支持曝光→点击→加购→下单和改搜分析；
- 版本验收使用固定用例和阈值；
- 能区分“结果相关性不好”和“服务响应太慢”；
- 灰度期间有观察窗口、告警条件和回退决定人；
- 每次发布留下验收结论，不只在聊天中口头确认。

## 8. 三名产品如何共同工作

### 8.1 每周协作节奏

| 时间 | 活动 | 主要产出 |
|---|---|---|
| 周一 | 30 分钟问题分诊 | 本周 Top Query、责任人、优先级 |
| 周二至周三 | 分角色整理和复核 | 标签、规则、相关性、交互或埋点结论 |
| 周四 | 与对应开发联合回归 | 指标结果和失败样本分类 |
| 周五 | 版本评审 | 是否通过、已知问题、下周样本和规则 |

### 8.2 问题如何归类

- **理解错误**：品牌、类目、场景或属性识别错，交给产品 1；
- **找不到**：正确商品未进入候选，交给产品 2 与召回开发；
- **顺序错误**：正确商品已进入候选但排名低，交给产品 2 与排序开发；
- **违规商品**：无库存、超预算、无权限等仍出现，产品 2 优先处理；
- **交互/数据问题**：联想、空态、埋点、慢请求体验，交给产品 3；
- **跨阶段问题**：由主负责人建立问题记录，三人共同确认最终归因。

### 8.3 产品交给开发的内容必须可执行

不要只写：

> 搜索结果不够准确，希望优化一下。

应写成：

> Query：`50 元以内员工福利保温杯`。期望：有库存且价格不超过 50 元的保温杯出现在前 10；实际：第 2 位商品售价 89 元。判断：违反预算硬条件。数据版本：Gold-v1.0；环境：联调；复现时间：待填写。

开发收到后应能直接复现、定位、修复和回归。

## 9. 高质量金标 Query 的生产流程

### 步骤 1：收集

从脱敏搜索日志、客服/销售反馈、采购场景和商品库组合中建立候选池。保留频次、来源和场景，但移除用户、企业、订单等敏感信息。

### 步骤 2：分层抽样

不要只按频次取前几百条。建议同时抽取高频、长尾、零结果、改搜、多条件、精确编号、错别字和否定表达。

### 步骤 3：去重与分组

对空格、大小写、全半角和常见符号做规范化；把同模板换品牌或数字的 Query 放入同一 family，防止训练和测试泄漏。

### 步骤 4：AI/规则预标注

用规则或离线大模型生成候选标签、改写和难例建议，减少人工机械工作。预标注必须保留来源和版本。

### 步骤 5：人工初标

产品 1 标注实体，产品 2 标注硬条件和候选商品相关性，产品 3补充 Query 场景、交互和数据标签。

NER 批次由开发预先拆成个人 Label Studio 项目，并抽取固定比例双标；产品不在同一个无分工任务池里抢任务。每句 Query 可以框选多个实体，但每个框选区域只选择一个标签。标完后，开发只把冲突样本导入单独的仲裁项目，交给产品 1 集中仲裁。产品无需执行脚本或查看代码仓库。

### 步骤 6：复核与仲裁

高风险和困难样本双人复核。意见不一致时记录争议，由对应产品主负责人仲裁，并把结论写回规范。

### 步骤 7：冻结和版本化

Gold 数据记录版本、日期、样本量、标签分布、修改原因和负责人。测试集冻结后不用于调参。

### 步骤 8：错误回流

线上或联调失败 Query 进入困难样本池。先判断是数据、理解、召回、规则、排序还是体验问题，再决定是否加入训练或回归数据。

## 10. 前两周产品具体安排

### 第 1 天：统一口径

- 三名产品确认各自主责和备份；
- 产品 2 主持价格、库存、状态、SPU/SKU、租户渠道决策；
- 产品 1 冻结第一版实体标签；
- 产品 3 冻结联想和结果页状态清单；
- 共同确定数据交付人、脱敏方式和版本命名。

### 第 2～3 天：建立第一批样本

- 产品 1：整理 200 条 NER Query，完成预标注和初审；
- 产品 2：整理 100 条 Golden Query，定义硬条件和候选评分；
- 产品 3：完成联想/搜索验收用例和第一版埋点表；
- 三人共同整理高频词、零结果和改搜 Top 清单。

### 第 4～5 天：双人复核与基线

- 产品 1 与 NER 开发复核标签边界和歧义；
- 产品 2 与规则/ES 开发跑第一份 Recall/NDCG/违规率报告；
- 产品 3 与性能开发跑冷/热缓存和失败降级体验；
- 周五冻结 Gold-v1.0、Rules-v1.0 和 Acceptance-v1.0。

### 第 2 周：模型、ES 和规则联调

- NER 数据扩充至约 2,000 条 POC 规模，产品 1重点看困难切片；
- ES 使用真实 Query 调整检索，产品 2关注正确商品是否进入候选；
- 规则权重调整，产品 2检查硬规则和前 10 排序；
- 产品 3验证联想、响应时间、降级、埋点和页面状态；
- 周末联合评审：演示、指标、失败样本、是否通过和下一阶段计划。

## 11. 产品团队验收红线

- [ ] 没有确认价格、库存、状态和租户口径，不进入生产灰度；
- [ ] 没有冻结 Gold Query，不宣称模型或搜索效果提升；
- [ ] 未经人工复核的 AI 生成 Query，不作为最终测试答案；
- [ ] 违反硬条件的商品不能靠“排序靠后”代替过滤；
- [ ] 没有真实规模压测，不承诺生产 P95/P99；
- [ ] 搜索结果失败时，异步 AI 文案不得阻塞或替代商品结果；
- [ ] Query、用户和企业信息未完成脱敏，不进入标注或日志分析；
- [ ] 没有回退方案和验收记录，不进入全量发布。

## 14. 产品常用名词表

| 名词 | 简单解释 |
|---|---|
| Query | 用户在搜索框输入的文字 |
| NER | 从 Query 中找出品牌、类目、场景、属性等实体 |
| Gold Query/金标 | 经过人工确认、可作为评分答案的 Query |
| 召回 | 从大量商品中先找出一批可能相关的候选 |
| 排序 | 把候选商品按照相关程度和业务规则排先后 |
| Elasticsearch/ES | 适合大规模全文检索和组合过滤的搜索引擎 |
| 缓存 | 保存热门 Query 的已有结果，减少重复计算 |
| F1 | 综合模型“标得准”和“漏得少”的指标 |
| Recall@K | 正确商品是否进入前 K 个候选 |
| NDCG@K | 前 K 个结果整体排序是否合理 |
| P95/P99 | 大部分请求和最慢长尾请求的耗时水平 |
| Shadow | 模型在后台运行并比较，但不影响用户结果 |
| Canary/灰度 | 只让少量真实流量使用新版本，观察后再扩大 |
| 降级 | 模型、ES 或 Redis 失败时改走备用路线 |
| SPU/SKU | SPU 是商品款式，SKU 是颜色/规格等具体可售单元 |

## 15. 产品团队最终要能回答的问题

1. 用户的这句话被理解成了哪些条件，是否正确？
2. 正确商品是没有找到，还是找到了但排序不够靠前？
3. 结果中有没有违反价格、库存、状态、租户或渠道硬条件的商品？
4. 当前版本相对上一版本在哪些固定指标上变好或变差？
5. 用户看到的联想、空态、错误和降级体验是否符合约定？
6. 数据是否脱敏，Gold 是否经过人工复核并已冻结版本？
7. 本次发布如果出现问题，谁决定回退，回退到哪个版本？

当三名产品能够用样本、规则、指标和版本回答这些问题时，开发团队才能稳定地优化模型、召回、排序、缓存和搜索体验。
