# AI 商城智能搜索：项目流程与团队分工（会议版）

> 版本：V1.0<br>
> 基线日期：2026-07-22<br>
> 参会角色：5 名开发、3 名产品<br>
> 会议目标：统一“项目现在有什么、下一步做什么、每个人负责什么、如何验收”

## 1. 先统一结论

当前仓库已经是一套**可以运行、测试和并行开发的 POC 框架**，但不是可直接生产上线的搜索系统。

- 已经具备：Java 8 在线主链路、规则/词典 NER、公司 `cdsgoods` 表适配、MySQL 有界召回、ES mapping 与 REST 召回、规则排序、Caffeine/Redis 缓存骨架、关键词联想、降级和离线标注/评分工具。
- 尚未具备：基于公司 Query 微调的 MiniRBT 模型、生产商品全量/增量同步、真实相关性金标、682 万 SKU 联调压测、生产监控与灰度发布。
- 团队不需要等待模型训练完再开发。接口冻结后，NER、ES/同步、规则评测、缓存性能可以并行推进。
- 在线主链路不调用生成式大模型；大模型只在离线帮助标注、改写和生成训练候选，人工对金标负责。

本阶段成功的标准不是“AI 功能全部完成”，而是每条工作流都有负责人、输入、接口、验收数据和可回退实现。

## 2. 用户搜索时系统如何运行

```text
用户输入 Query
  ├─ 输入过程中：关键词联想（完全/前缀/中间/后缀/别名）
  └─ 提交搜索：
       请求校验与标准化
         → L1 Caffeine / L2 Redis 缓存
         → 规则词典 NER；未来并行接 MiniRBT
         → 路由判断
             ├─ SPU/SKU/条码/供应商 SKU：MySQL 精确直查
             └─ 普通自然语言：ES 主召回；MySQL FULLTEXT 有界兜底
         → 商品事实补全
         → 硬规则过滤（上下架、库存、预算、租户、渠道等）
         → 软排序（文本相关性、规则分、运营分、预算贴合度）
         → 返回 SPU 商品卡 + 最佳匹配 SKU + trace
```

设计原则：先在 200 ms 目标内返回商品结果；未来若增加导购文案，应走异步旁路，不阻塞商品列表。

## 3. 数据如何进入搜索系统

```text
MySQL 商品事实表
  ├─ SPU、SKU、库存、类目、品牌、属性、描述
  ├─ 全量构建 → ES 新版本索引 → 校验 → alias 切换
  └─ binlog/CDC 增量 → bulk upsert/delete → 失败补偿与对账

历史 Query 与人工业务知识
  ├─ 脱敏、抽样、去重
  ├─ AI 预标注/改写
  ├─ 人工复核形成 Gold 数据
  ├─ train/dev/test 固定切分
  └─ MiniRBT 微调 → ONNX → Java shadow → hybrid/canary

曝光、点击、加购、购买
  └─ 离线评测与规则/排序迭代，不直接污染冻结测试集
```

MySQL 是商品事实源；ES 是可以重建的检索索引；Redis 是加速层；模型制品必须带版本并能回退到规则 NER。

## 4. 当前完成度与缺口

| 模块 | 当前状态 | 生产前主要缺口 |
|---|---|---|
| Java API 与 Pipeline | POC 可运行 | 契约冻结、统一错误码、完整 metrics、超时预算 |
| 规则/词典 NER | 基线可用 | 公司 Query 回归、词典治理、冲突与否定样本 |
| 模型 NER | 接口、fixture、shadow/hybrid 已有 | 训练脚本、Gold 数据、ONNX 模型、Java 推理与一致性验证 |
| MySQL 召回 | demo/cdsgoods 双适配、有界查询 | 用精确 DDL/索引校验 SQL，真实数据 `EXPLAIN ANALYZE` |
| Elasticsearch | SPU+nested SKU mapping、REST 召回与回退 | 全量/CDC Worker、真实 analyzer/分片/容量评测 |
| 规则与排序 | 硬过滤、软打分骨架 | 业务规则确认、relevance judgment、Recall/NDCG 调参 |
| 搜索联想 | 类目/品牌内存基线，支持前中后缀 | ES ngram Source、热词/历史词、拼音与纠错策略 |
| 缓存 | Caffeine L1 + 可选 Redis L2 | 集群、key/TTL/版本规范、热 key、预热、故障演练 |
| 测试 | 单元测试与离线 NER 评分工具 | 契约/集成/相关性/压测/故障测试流水线 |
| 发布运维 | trace 基线 | Dashboard、告警、灰度、回滚、容量与安全审计 |

## 5. 五名开发如何认领

### 开发 1：架构与 Java 集成

**需要熟悉**：Java 8、Spring Boot、MyBatis、接口与 DTO 设计、超时/降级、单元和契约测试。

**先改善哪里**：

1. `RecommendPipeline`：统一阶段耗时、异常类型和降级原因；
2. `ProductSearchService`、`RecallOrchestrator`：冻结路由、候选数量和回退契约；
3. `IntentResult`、`ProductCard`、`SearchCriteria`：补齐 schemaVersion 与兼容规则；
4. 为 NER、ES、缓存的 stub/真实实现补契约测试。

**改进方向**：核心层不绑定具体模型/ES 客户端；所有外部依赖均有超时和回退；接口变更先改契约和测试。

**两周交付**：接口 V1、错误码、超时预算、Pipeline 集成测试、架构决策记录。

### 开发 2：数据与 NER 模型

**需要熟悉**：Python、Hugging Face Token Classification、BIO/span 标注、Label Studio 或 doccano、precision/recall/F1、ONNX。

**先改善哪里**：

1. `ml/`：补训练、评测、导出和制品校验脚本；
2. `EntityDictionaryService`：完善别名、标准 ID、冲突词和版本；
3. `NerModelClient`/`HybridIntentRecognizer`：接入真实 ONNX 前先跑 shadow；
4. 与产品 1 建立 500～2,000 条脱敏 Query 和第一批 200 条双人复核样本。

**改进方向**：先以 `hfl/minirbt-h256` 预训练权重做商城 NER 微调；价格、数量、ID 等确定性实体继续用规则；只有真实评测显示必要时才做蒸馏。

**两周交付**：标签规范 V1、2,000 条 POC Gold/Silver 数据、MiniRBT 基线报告、ONNX 接入计划。

### 开发 3：ES、召回与商品同步

**需要熟悉**：Elasticsearch mapping/analyzer/Query DSL、BM25、nested、Bulk、alias，以及 MySQL 索引、binlog/CDC、幂等与对账。

**先改善哪里**：

1. `es/mall-product-spu-template-v1.json`：用真实样本验证字段、分词、nested SKU；
2. `RestElasticsearchRecallChannel`/`ElasticsearchQueryFactory`：补过滤、超时和错误分类；
3. 实现 `SuggestionSource` 的 ES ngram 版本；
4. 新建全量 + 增量同步 Worker，先用 1 万条脱敏商品验证 upsert/delete/重放。

**改进方向**：一 SPU 一文档、SKU nested；MySQL 为事实源；新索引构建完成后通过 alias 原子切换；同步必须可重放、可对账、可回滚。

**两周交付**：真实集群索引、1 万样本、基础 BM25/联想、同步骨架与一致性报告。

### 开发 4：规则、排序与相关性评测

**需要熟悉**：商城价格/库存/状态/租户规则，搜索 Recall@K、MRR、NDCG，Java 规则配置与数据分析。

**先改善哪里**：

1. `ProductRuleEngine`：把硬规则、软权重和原因码配置化；
2. 建立 Query→候选商品的 relevance judgment（0～3 级）；
3. 建立 Recall@50/200、MRR、NDCG@10/20、零结果率、约束违规率回归；
4. 用固定金标调 `application.yml` 的权重，不凭个人感受调分。

**改进方向**：硬规则保证不能错，软排序允许实验；每次改模型、mapping 或权重都跑同一冻结测试集。

**两周交付**：100～200 条 Golden Query、规则清单、评测脚本/报告、第一版权重基线。

### 开发 5：缓存、性能与工程化

**需要熟悉**：Caffeine、Redis Cluster/Sentinel、JVM/GC、连接池、压测工具、监控告警、CI/CD 与密钥治理。

**先改善哪里**：

1. `SearchCacheService`：明确 key 维度、TTL 抖动、负缓存、版本失效和 Redis 故障退避；
2. 为 NER、DB/ES、规则、缓存、总耗时补 P50/P95/P99 指标；
3. 建立热门/长尾/精确 ID/复杂长句的压测集；
4. 准备 Dashboard、告警和故障演练。

**改进方向**：缓存 key 必须包含租户、渠道、规范化 Query、规则/模型/索引版本；任何缓存或外部服务失败不能拖垮主链路。

**两周交付**：生产缓存规范、基线压测报告、指标 Dashboard 草案、Redis/ES 故障回退演练。

## 6. 三名产品如何认领

### 产品 1：搜索意图与 NER 标注

**需要熟悉**：类目树、品牌和别名、用户搜索表达、标签边界、标注一致性。

**先做**：定义第一版搜索意图和实体标签；整理正例、反例、否定词、歧义词；与开发 2 双人复核第一批 Gold Query。

**交付**：标签规范、场景词典、歧义处理规则、每周新增困难样本清单。

### 产品 2：业务规则与相关性金标

**需要熟悉**：商品选品、价格口径、库存/上下架、租户渠道约束，以及“什么商品算相关”。

**先做**：确认 `sales_price`、可售库存公式、状态枚举、SPU 卡片 + 最佳 SKU 口径；为 100～200 条 Query 对候选商品打 0～3 级相关性分。

**交付**：硬规则真值表、Golden Query、零结果处理标准、排序验收报告。

### 产品 3：搜索体验、数据分析与验收

**需要熟悉**：搜索页/联想交互、曝光点击漏斗、埋点、实验设计、SLA 和验收流程。

**先做**：定义联想展示与键盘行为、搜索空态/降级态；定义曝光、点击、加购、购买和改搜事件；明确性能与体验验收线。

**交付**：交互说明、埋点协议、核心指标看板、版本验收清单。

## 7. 建议配对关系

| 配对 | 共同产出 | 不应互相等待的做法 |
|---|---|---|
| 开发 1 + 全体 | 接口、版本、错误码、集成基线 | 用 stub/fixture 保持 Pipeline 可运行 |
| 开发 2 + 产品 1 | NER 标签、数据、模型 | 先以规则结果预标注，再人工复核 |
| 开发 3 + 产品 2 | ES 字段、召回与商品口径 | 先用 1 万条样本，不等全量同步 |
| 开发 4 + 产品 2 | 规则与相关性评测 | 先冻结 100 条 Gold，不等模型完成 |
| 开发 5 + 产品 3 | 性能、缓存、埋点和验收 | 先用现有规则/MySQL 基线压测 |

产品负责人不是“写完需求后等待”，而是持续提供可判断对错的数据。开发负责人不是“模块代码写完即完成”，而是交付可测、可观测、可降级的能力。

## 8. 明天会议建议议程（60 分钟）

1. **0～5 分钟：目标**——确认本阶段是生产化 POC，而不是立即上线。
2. **5～15 分钟：流程演示**——输入联想、一次搜索、trace、精确 ID 路由、ES/MySQL 回退。
3. **15～25 分钟：现状与缺口**——逐项说明“已有骨架”和“尚未验证”。
4. **25～40 分钟：分工认领**——5 个开发角色、3 个产品角色各确认主负责人和备份人。
5. **40～50 分钟：两周计划**——确认每条工作流的输入、交付、依赖和验收方式。
6. **50～60 分钟：决策与风险**——冻结业务口径、环境、数据交付日期和 SLA。

会议不要陷入模型参数或 ES 分词器细节；这些由负责人通过统一评测集给出比较结果。

## 10. 会后两周安排

### 第 1～2 天：冻结与基线

- 运行现有项目和 23 个测试；所有人走一遍搜索与联想。
- 开发 1 冻结 DTO/接口/错误码；产品 2 确认价格、库存、状态口径。
- 产品 1/2 分别准备 NER Query 与相关性 Query；开发 5 记录当前延迟基线。
- DBA 审核 `sql/cdsgoods_search_indexes.sql`，只做审核与小样本验证，不在高峰直接改生产表。

### 第 3～5 天：各模块第一版

- 开发 2：200 条双人复核 NER 样本，跑通数据校验和切分。
- 开发 3：1 万条样本写入 ES，跑通搜索与联想 Source。
- 开发 4：100 条 Golden Query，生成首份 Recall/NDCG 报告。
- 开发 5：完成缓存 key 规范和四类 Query 的压测基线。
- 开发 1：完成跨模块契约测试和失败降级用例。

### 第 2 周：集成与比较

- NER：扩至约 2,000 条 POC 数据，训练 MiniRBT 首版并在 shadow 比较规则。
- ES/同步：补 bulk、upsert/delete、重放、对账；用真实 Query 调 BM25。
- 规则：依据冻结金标调整硬规则和权重，输出前后对比。
- 缓存/性能：接 Redis 测命中、雪崩/热 key/故障回退，形成 P95/P99 报告。
- 周末集成：现场演示、指标报告、问题清单、下一里程碑。

## 12. 当前风险边界

- 当前 SQL 依据截图和关系梳理完成 V1，仍需精确文本 DDL、现有索引和真实 `EXPLAIN ANALYZE` 校验。
- 不把 682 万 SKU 全量读入 JVM，不使用 `%LIKE%` 做主召回，不逐商品 N+1 查询。
- 未经公司 Gold Query 评测的通用中文 NER 模型不能宣称业务可用。
- 不将数据库、Redis、ES 密码提交 Git；个人本地配置继续由 `.gitignore` 排除。
- MySQL 建索引、ES 全量重建、缓存批量清理必须走审批、低峰和回滚方案。
- “测试通过”只说明代码基线正常，不代表真实相关性、容量和生产可靠性已经验证。
